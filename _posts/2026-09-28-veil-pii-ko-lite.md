이 글은 CPU만으로 돌릴 수 있는 경량 한국어 PII(개인정보) 탐지 모델 **Veil-PII-Ko-Lite**를 개발한 과정과 결과를 정리한 리포트입니다.

## 1. 개발 동기

- 매 프로젝트마다 폐쇄망 환경에서의 PII 모델 적용은 필수 요소. **But** 아쉬운 한국어 PII 성능
- 폐쇄망에서 GPU 없이 가볍게 구동할 수 있는 PII 모델 필요
- 다양한 한국어 PII Category에 대한 탐지 기능 필요
- 좋은 PII 성능을 보이는 것으로 알려진 모델들을 후보군으로 두고 탐색

| 후보 | 내용 | 적용 한계 |
| --- | --- | --- |
| BCCard MoAI-Privacy-Filter (2026-08) | openai/privacy-filter(1.4B) 한국어 파인튜닝, 29 라벨, Apache 2.0 | 1.4B 규모로 CPU 서빙 부담. 모델카드가 상업 사용 시 고지를 요구. / 실제 대화체(KDPII)에서는 F1 0.45로 낮은 탐지 성능 |
| FrameByFrame privacy-filter-korean (2026-04) | 동일 1.4B 백본, KDPII 학습, 9 라벨 | 주민번호·카드·사업자번호 등 금융 필수 라벨이 없음. |
| Azure AI Language PII | 관리형 API, 한국어 지원 | 한국어 주소 F1 0.08, 계좌 미검출 등 한국어 PII 탐지 성능 낮음 |
| Microsoft Presidio | 규칙 + NER 프레임워크 | 대체재가 아니라 NER 모델을 끼워 쓰는 프레임워크 개념. 한국어 인식 기능이 있긴 하지만 정형 카테고리 5종만 탐지를 지원함. 전후처리에 특화되어 있어 PII 모델과 패키징에 활용 예정 |

**결론적으로 "경량 · 한국어 강함 · 카테고리 넓음 · 라이선스 부담 없음" 네 조건을 동시에 만족하는 공개 모델이 없어 직접 개발하기로 하였습니다.**

## 3. Backbone 선택

작은 크기 및 한국어를 지원하는 PII backbone 모델 5종을 비교분석하였습니다.

후보 5종을 같은 데이터(2종 - KDPII, BCCard val 데이터), 같은 하이퍼파라미터로 2 epoch로 학습하여 비교하였습니다.

최종 판단 기준은 F1 Score 기준 정확도 및 모델의 크기를 가장 중요한 요소로 두어 평가하였고, 최종적으로 **'ko-electra-base-v3'** 모델을 최종 backbone 모델로 선택하였습니다.

*백본에 대해 PII 탐지(라벨을 인식할 수 있도록)가 가능하도록 동일 조건으로 fine-tuning 진행했고, train loss는 동일하게 떨어졌습니다.  
다만, validation set에 대해서는 아래와 같이 Ko-Electra-base-v3 모델이 가장 좋은 성능을 보였습니다.*

| 백본 | 파라미터 | 라이선스 | KDPII test F1 | BCCard val F1 | 판정 |
| --- | --- | --- | --- | --- | --- |
| **monologg/koelectra-base-v3** | 110M | Apache 2.0 | **0.8789** | 0.9613 | **채택** — 가장 작고 KDPII 스코어는 최고 득점 |
| kakaobank/kf-deberta-base | 185M | MIT | 0.8798 | 0.9661 | +0.1~0.5pt 이나 INT8 245MB로 크기 목표 초과 |
| lucid/deberta-v3-base-korean | 185M | Apache 2.0 | 0.8533 | 0.9527 | 탈락 |
| beomi/KcELECTRA-base | 110M | MIT | KoELECTRA 하회 |  | 탈락 (구어체 특화 이점 확인 안 됨) |
| microsoft/mdeberta-v3-base | 276M | MIT | exact 0.39 → 오프셋 보정 후 회복 |  | 탈락 — 크기 2.5배, SentencePiece 선행공백 오프셋 문제로 디코더 보정 필요했음 |

## 5. 학습

### 5-1. 학습방식 → Full Fine-Tuning

- Ko-Electra-base-v3 백본 모델의 경우, 기존 transformer encoder에 이진판별(토큰 간 동일여부)이 가능한 헤더가 붙어있었습니다. (768 → 1). 해당 헤더 부분을 PII category 분류 목적에 맞게, 768 → 129dim의 헤더로 변경하였습니다.
- 그리고, 가중치 업데이트는 전체 모델 architecture에서 기본적으로 Embedding layer, Encoder layer를 학습합니다. (헤더만 학습하는 게 아니라, 전체 레이어에 대해 기울기 계산을 진행하여 백본 전체를 갱신함!!)
- 그리고 위에서 언급한 토큰 분류헤더에 대해, 각 토큰별로 총 129개 라벨에 대한 확률값을 예측하는 형태로 학습을 진행하였습니다.
  - 라벨이 129개인 이유는, 총 32개의 카테고리 라벨이 있고, 각 라벨별로 **'시작 B(Begin)'**, **'중간 I(Inside)'**, **'끝 E(End)'**, **'단일 S(그냥 혼자서 하나의 엔티티를 가지는 경우, Single)'** 총 4가지 정보로 분류되고, 마지막으로 엔티티가 아님에 해당하는 라벨까지 더해서, 32 x 4 + 1 = 129개의 예측해야 할 라벨이 발생합니다.
- 다만, 모델의 output이 129개 라벨에 대한 토큰별 확률값이고, 각 토큰별 129개의 확률값 중 제일 높은 확률의 라벨을 고르는 방식(argmax)을 선택할 경우, 토큰의 시작-중간-끝 요렇게 문법(?)에 맞게 배치되어야 하는데, 단순 높은 확률값으로만 채택할 경우, 단일 토큰의 예측라벨이 IBBS...BBI, 뭐 이런 식으로 말도 안 되는 토큰 배치가 발생할 수 있습니다.
- 이에, Viterbi 알고리즘을 적용하여, 앞단의 토큰의 라벨이 예측되었을 때, 뒷 토큰의 경우 그 자리에 올 수 있는 라벨 중에서 가장 높은 확률을 가진 라벨을 채택하는 방식으로 보정하여 분류하였습니다.
- **Tuning Params**
  - Loss Function : `nn.CrossEntropyLoss`
  - Label Smoothing : 0.05 (v1~v3a) → 0 (v3b·v4)
  - Optimizer : AdamW
    - weight decay : 0.01
    - dropout : 0.1
  - learning rate : 3e-5 → 5e-5 (v3b·v4)
  - warmup : 10%
  - epoch : 5→6
  - Loss 제외 토큰 반영(ignore\_index=-100 처리)
    - padding, [CLS], [SEP] 토큰은 학습 제외

### 6-4. 양자화 및 Latency

- Dynamic INT8로 양자화를 진행한 경우, 모델크기는 113까지 감소했으나, activation까지 양자화(정수)되면서 recall이 대폭 하락했습니다. 원인은 129개 라벨의 1,2등의 prediction score가 매우 근소한 차이라, 성능하락이 컸습니다.

## 7. 최종 결과 분석

### 7-1. 최종 결과

- CPU 환경에서 운용이 가능한 110M의 작은 PII 모델 확보
- 1.4B에 달하는 모델 대비 더 많은 Category를 지원(32개)
- 경쟁 모델 대비 작은 크기(10배)로 더 높은 탐지 성능 확보

### 7-2. 매우 작은 모델로도 높은 성능을 낼 수 있었던 이유

- PII detection 시, 비교모델(bccard)의 경우 autoregressive하게 생성하여 output을 도출하는 방식인데, **veil 모델의 경우, 각 토큰에 PII 라벨을 찍는 token classification 방식으로 탐지합니다. 즉, veil에서 필요한 출력은 {start, end, label}로 단순**하나, 비교모델은 문장을 생성한 뒤, 원문에 다시 맞추는 alignment 과정이 필요한데, 이 부분에서 mask token 길이가 원문과 다르거나, 조사, 공백, 어순이 틀어지는 현상으로 인해 낮은 성능을 보일 수밖에 없습니다.
- `openpii-1.5m-ko` 데이터 전수검사를 통해 약 **30%가량의 불량데이터를 검출하여 제거하여, 학습 노이즈를 최소화**
- 실제 대화체에 개인정보가 포함되는 형태의 학습데이터를 대거 추가하여, 구어체의 긴 문장이 포함된 벤치에서도 높은 성능을 보임.
- 합성데이터를 LLM으로 형태만 맞추어 무작위 생성하지 않고, 각 **데이터별 포맷 규칙(프로그래미틱하게 작성)하에 작성하여 최대한 리얼월드 데이터와 유사하게 생성하고, 할루시네이션 가능성을 차단하였습니다.**
  - 예) Luhn 알고리즘 활용하여, 실제 카드번호와 동일한 형태로 생성 → `ISO/IEC 7812 — 앞 6자리 BIN(발급사) + 계좌번호 + 마지막 체크디지트`

### 7-3. 추후 보완사항

- 새롭게 추가된 카테고리 중, S/N 기기단말번호 또는 가입번호와 같은 회사마다/도메인마다 정형화된 포맷이 아니라, 예측이 어려운 부분에 대해서도 학습에 추가했으나, 실제로 예측하지 못하는 케이스가 더러 발생했다.
- 비정형 타입의 카테고리의 경우, 전후 맥락 및 토큰의 위치정보 등을 통해 최대한 예측했으나, 아래 실제 테스트 결과와 같이 아직 탐지하지 못하는 케이스들이 확인되었고, 전체 카테고리의 탐지성능을 균일하게 끌어올리는 것이 추후 과제로 보여진다. (물론 실제 고객 환경에 적용 시, 해당 문제가 발생할 경우 모델단이 아닌 presidio를 통한 후처리를 통해 domain specific한 부분들은 어느 정도 처리가 가능하긴 함)
- 마지막으로, 실제 기업 내부 프로덕션에 올려서 실 데이터 기반으로 검증이 필요함.
